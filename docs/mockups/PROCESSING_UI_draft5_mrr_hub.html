Design annotations

  1. `mrr_processing` comes back with its spawner. System-routed to an ORO Associate when intake detects child_count > 1, eligibility applies — exactly the catalog design; the 2026-07-19 deletion note says re-add the key alongside the code that spawns it, and this screen is that code's reason. is_mrr stays derived — a fact, never a mode.
  2. Parent line + child lines, and the queue renders the same shape — §14.3's rule that the hub and the queue are one design, not two screens. The disabled “Hub —” placeholder on parent lines in today's queue becomes this link.
  3. RULE A The statutory clock lives only on the parent. Children carry budget clocks (named budget_clock, never “tolling”) with days ahead/behind from estimate-profile budgeted dates. The parent chip is the only navy statutory treatment on the screen.
  4. MRR bypasses intake review, so the requestor-level checks render here — the same eligibility / ledger / waiver components from Draft 1, as compact chips on the parent card (expand on click). Nothing requestor-level lives on a child.
  5. DECIDED §14.2 Suggest-and-confirm. The classifier runs identically on every child; on an MRR the result is suggested, and the RM accepts (one click / accept-all), overrides (team or person — manual assignment bypasses eligibility by design), or takes it personally. Low-confidence suggestions arrive withheld (item 3). This is also the answer to the per-child routing_review “duplication”: three routing decisions are correct; three tasks in a worklist was the presentation problem, and these child lines are the designed presentation.
  6. Non-system contributor (§14.4.2): estimate-gathering assigned by email to someone with no login — secure, expiring, single-use token link; their submission completes the task. Link state (sent / opened / expired) is visible on the child line. Needs the token substrate; nothing else in any spec covers this case.
  7. “Take it myself” still spawns a self-assigned task. Work with no task is invisible to the budget clock — the one signal that catches a stalling child. ⚠️ The spec flags this as Claude's call, not Kevin's — ratify or reverse it here.
  8. One parent estimate from per-item inputs (§14.4.1): items feed costs (profile / external / RM-entered); the parent creates one estimate through the standard engine and one notice — consistent with the parent being the financial processor and the RM the sole communicator.
  9. RULE C adjacent Verify ≠ Approve, structurally. Staff Verify; the requestor approves — in some states approval is the statutory event that begins processing. Two words, two buttons, two actors; the UI never offers staff an “Approve”.
  10. The critical-path readout is the point (Kevin's scenario, §14.3): the item blocking the parent — and therefore reconciliation and final billing — is named, with its days-behind. The parent is never “ahead” because most items are; parent variance is the critical-path child. Drafted as the ghost panel so the intake-time and later-life faces of the same screen are both visible.
  11. HOLD, not early release (§14.4.5 inverted): as_ready releases each completed item on its own; the deliberate act is holding one, guarded, and never because a sibling is unpaid — §5.9's coverage test is per item.
  12. One request, one voice (§14.1): Contact-requestor exists only on the hub; item task screens carry “email the Request Manager”. Draft 1–4 screens comply already for MRR children — their clarification buttons route through the RM when the parent is an MRR.
  13. High priority (§14.4.6): the parent flag feeds the AI report monitoring all high-priority MRRs — flag here, report drafted with the reporting surfaces, not this session.

Flagged, not designed here: the estimate worksheet's own layout (per-item grid); the token substrate; the mixed-outcome notice question (§14.5 — which letter a citizen gets when one item is delivered and another denied — belongs to the notices field-design pass); the org-wide bottleneck report.
