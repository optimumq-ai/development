Design annotations

  1. DECIDED 7/28 intake_review is a real task, spawned ONLY WHEN NEEDED (default). A new routable task type intake_review, owned by ORO Associate, on My Tasks (the only router); pool assignment, smart routing considered. It spawns only when a trigger fires: (i) the AI can't determine the fulfillment team · (ii) an eligibility review came back · (iii) a waiver/commercial decision is pending in intake_review mode · (iv) a sensitivity flag. Everything else routes straight to its team with no stop. A city can flip a setup option to always (every non-MRR request pauses here). Trigger (i) absorbs today's separate routing_review task — “can't route” becomes one trigger of this task rather than a task of its own. The queue's “Why it's here” column and the task screen's “Here because:” line surface the trigger, because on an exceptions queue the reviewer's first question is which exception. Shared pieces (clock chips, decision badges, portal-results bar) ship as a component library, not a shared screen.
  2. RULE A A due date is not automatically a deadline. Two visual grammars, never interchangeable: navy solid left-bar = statutory deadline (kind response/agency_action, with citation); grey dashed = city service target — not a legal deadline; thin outline = requestor's window. Copy comes from computeStatus.overdueMeaning, never hardcoded. Ohio shows an honest “no deadline” rather than inventing a date.
  3. DECIDED 7/28 Parent-level task, non-MRR only. Intake review is a parent-level task: the screen leads with parent-level info (requestor, clocks, eligibility, ledger, waiver) and the single record item's detail sits behind a click-to-expand (drawn expanded on the Texas tab, collapsed on the Ohio tab — both really toggle). This path never carries more than one record item; MRR requests do not spawn intake_review and follow their own Request-Manager flow (separate draft).
  4. Prelim search lives inside the record item's expand, reusing the record-search screen's portal-results bar (Selected / Not Selected + queries already tried). Intake's version answers one question: can the library already answer this? The deep search stays in the Record Search task.
  5. RULE C Advisory ≠ automatic — eligibility. Three treatments: ghost/dashed “Recorded — nothing to decide” (advisories), amber “Needs your confirmation” (reviews, with the confirm control), and blocks never appear here — a blocked submission is refused at the portal. External decisions always name their decider and citation (the vexatious list is the court's).
  6. RULE C + E Ledger. Money triggers (TX deposit rule) are system-computed per statute — shown with the navy “System · statute-triggered” badge, citation, and an explicit “nothing for you to decide.” Denial-shaped ledger findings would appear amber, a person confirms. Anonymous requests state plainly that history does not apply — never “balance hidden.”
  7. Inline approval (mode: intake_review). The fee-waiver decision lives on this screen with no extra hop. In routed_task mode (today's live default) this panel is absent and a Fee-Waiver Approval task routes to ORO Finance instead. Sequencing is enforced either way: the estimate cannot be sent while the waiver is undecided, and a denial folds into the estimate notice.
  8. RULE C Decided-by is first-class. Every decision surface carries a badge: a person (named), by statute (mandatory categories on verified evidence — fires even if the program is off), system · statute-triggered (money math), recorded only. The system records and applies; it is never shown as having decided a judgment call.
  9. Resolution gates. “Proceed → Fulfillment” is the stage transition (central applyStageTransition); it stays blocked while an inline decision (waiver, eligibility review) is open, and says why — same pattern as the record-search screen's Found gate. DECIDED 7/29 No manual hold button. Hold is a system state with a named cause: marking Vague / Overly Broad holds the request automatically pending the requestor's response; everything else that should stop a request already blocks Proceed with its reason. If a genuine manual case emerges it returns with a required reason.
  10. RULE B Panels are branch-gated, three-valued. Only an explicit false hides a panel (Austin: commercial-rate; Columbus: waiver, commercial, anything AG). null = unknown = render everything as today — 19 of 21 seeded cities are null, and this screen must not strip panels from them.
  11. Defect marking lives on the record item — and doesn't depend on this screen. Vague / Overly Broad are distinct legal defects (per the record-search spec), visible on the item's row inside the expand. For the majority of requests that skip intake review under only-when-needed, the same markers already exist on the Record Search task screen (built 7/14), wired to the full per-jurisdiction clarification machinery — so a defect discovered after team assignment fires the identical process, just from the first fulfillment task instead of from intake.
  12. Branch-gated denial ground. “Deny — too vague” appears only where clarification_denial: true (Ohio). It is denial-shaped, so it is a person's act through Denial compose — never automatic.
  13. DECIDED 7/28 Auto-complete. A portal request whose requestor indicated that an attached/selected record fulfills the search never stops here: under only-when-needed it's simply one more no-trigger case (and in always mode the task is spawned and completed automatically, audit trail intact). Binds to the portal's selected-records + search-intent complete substrate (R9).
  14. The trade only-when-needed makes, stated honestly. In a hard-clock state, a vague request that slips past intake (confidently classified, no triggers) is discovered by the searcher on day 3–6 of Texas's 10 business days rather than day 1 — a tighter clarification window. Mitigations: vagueness and unroutability usually arrive together (R-1082 on the Ohio tab — the vague ones mostly are the can't-route ones, so they stop here anyway), and the downstream markers fire the identical clarification process. Cities that want day-1 defect review flip the setup option to always.
  15. KEVIN 7/29 The AI's three routing facts are editable in place. Classified-as / Record owner / Will-route-to sit in one "Edit info below" frame: display state (Ohio tab) shows the values with the edit button; editing (Texas tab) turns each into a dropdown backed by a real list — the record-type taxonomy · City Departments · Fulfillment Teams. Corrections matter beyond this screen: smart routing matches specialization against the eligible staff of the chosen team, and the classification travels with the item as search context for whoever fulfills it. Replaces the lone Change-route button.

Out of scope for this role (drafted next, separately): the MRR / Request-Manager intake flow, the go-live confirm-each-knob checklist (rule D — an admin surface, TX and OH each carry 9 unconfirmed knobs today), the estimate/waiver interaction on EstimateTaskPage, Denial compose, and the parent financial view.
