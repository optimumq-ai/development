Design annotations

  1. Role and queue. Estimate tasks belong to [Team] Fulfillment Staff holding the Estimate Creation subset (ORO Associate for MRR — out of scope here, same as Draft 1). Team-scoped pool + smart routing, same as every routable type. This queue is normal traffic, not exceptions — under only-when-needed intake, most requests come here first.
  2. Provenance is a column. “Path here” says whether a human has vetted the request: Auto-routed — first human review (nobody has) vs Via Intake Review (name) (with what was decided there, e.g. a waiver denial that will fold into this estimate's notice). The estimator's duty changes with it, so it is queue-level information, not fine print.
  3. DECIDED 7/28 The estimate task is the auto path's checkpoint. The first-look banner + the same defect markers as intake review (Mark Vague / Mark Overly Broad) on the record item. Marking a defect pauses the estimate task and fires the per-state clarification machinery (clock effect per jurisdiction; the banner never claims the clock stops where it doesn't). “You can't price what you can't parse” — raising the defect is part of this task, not a failure of it.
  4. The estimate is built pre-search from the estimate profile (auto path: estimate precedes record search — already how the engine sequences it). Predicted basis is shown and editable; nothing pretends the search happened. Where the profile assessment is automated, the task arrives as “Review auto-generated estimate” instead of “Create estimate”.
  5. Caps and allowances render as staff-entered facts (ledger classes B/C are config stubs by decision): the TX 36-hour tracker shows its value with a staff-entered badge — never implying the system counted it.
  6. Waiver panel has four states, all provenance-labeled: not requested (statutory categories still armed, by statute fires on verified evidence regardless of program or confirmation) · decided at intake (person badge with name; denial folds into this notice) · pending in routed_task mode (ORO Finance task open — Send blocked, 409 WAIVER_UNDECIDED, and the gate says so in words) · granted (fees zeroed at notice time, notice says so).
  7. RULE C+E Deposit gate. Prior-balance demands are system-computed per statute with citation and “nothing for you to decide” — and they ride the estimate notice, never a separate letter. Anonymous requests: the panel is absent because nothing applies, and the ledger panel says so plainly.
  8. One notice. Estimate + itemization + deposit demand + waiver outcome + respond-or-withdrawn window assemble into a single communication (the built feeNotice behavior). The send gate lists what's blocking in words, not just a disabled button.
  9. “Too large” is not a mark on this screen — it's the estimate. After send, the requestor keeps control at the acceptance gate (proceed / narrow / withdraw). In the states where a burden denial exists (IL), the conference-to-narrow gate lives on Denial compose, not here — this screen's estimate is the evidence that conversation uses.
  10. RULE A adjacent Chargeability is jurisdiction config, rendered as law, cited. Ohio's estimate builder simply has no labor lines (actual cost only, R.C. 149.43(B)(1)); Texas has personnel time at the AG-schedule rate. The builder never offers a line the state forbids.
  11. Delivery caps (OH) surface at estimate/delivery time as a per-requestor monthly count — identity-anchored only; an anonymous request shows no count and implies none. Config-stub honesty: manual values until a city elects automatic counting.

Flagged for a later draft, not designed here: the refund/credit path when a later exemption denial shrinks a paid deliverable (belongs to the parent financial view, a BUILD item); the Denial-compose prerequisite gates (IL conference-before-burden-denial); and the MRR estimate flow.
