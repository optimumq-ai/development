Design annotations

  1. KEVIN 7/28 Closing happens where the evidence lives. No separate close surface to navigate to: Record Search carries No-records and Not-our-records; Legal Review / Denial compose finalize Denied (deny + close + notify in that UI, no extra hop); delivery and the lapse endings are automatic. The §5.8 vocabulary and every evidence gate survive unchanged — the gates simply moved into the popup of the task that produces their evidence.
  2. Two close buttons on the search task, zero one-click closes. Every close is a confirm popup stating what will be written and what will be sent — disposition + notice as one act (a closure is the response the requestor gets).
  3. RULE-pattern The no-records popup carries the full gate: non-empty effort trail + every duty-carrying description answered + the required reasoning note, and the firewall restated: an answered description is a claim, never effort. The popup is the gate — closing without the note stays impossible.
  4. KEVIN 7/28 Supervisor approval is department config: close_approval: direct | either | approval_required per department (per evidence-gated ending). “Either” draws both buttons and lets the closer choose — your two-button sketch; “approval required” makes the supervisor's approval the recorded act. Pending closes are visible states, not limbo. Default is an open question below.
  5. Not-in-custody closes from the search task too (your “tbd” — drafted yes): the searcher who discovers the records belong elsewhere names the custodian in the popup; referral record + letter ride the close.
  6. KEVIN 7/28 Delivery is condition-triggered, never asserted. Four conditions: all flow tasks terminal (done or auto-bypassed with recorded basis) · balance ≤ 0 · no pre-send review gate · non-MRR. Payment due ⇒ pending until the balance clears, then ships untouched. Zero-fee (waiver/de-minimis) ⇒ the payment step auto-completes with its basis and the pipeline runs straight through — your record-search-only worked example is Frame B.
  7. RULE C Auto-bypass is honest: every task the pipeline skips is completed as a record with its basis (statutory waiver → by-statute badge; $0 balance → system-condition badge; no exemption flags → recorded badge). The pipeline never silently omits a step — it completes it with a reason someone can audit.
  8. Delivered is written by the release event — release + funds check + notice + delivered_at + installment_no, one event; a redacted release is still Delivered (withholding log carries the detail; no “partially granted” disposition exists). Unchanged from rev 1; what changed is that the event now usually fires itself.
  9. The pre-send review gate is config, default none. Where a city (or a statute research surfaces) requires a human look before release, the pipeline pauses at a review task instead of shipping — the hook exists so compliance never has to fight the automation. It is off unless someone turns it on.
  10. KEVIN 7/28 No-response and Non-payment are sweep-only now. The rev-1 manual path is removed: they close from data (grace + buffer; the 60-day window), with the numeric basis, the attested-config badge, and the notice trail on the record. Resolves rev 1's open question 3.
  11. This screen is now the Disposition record: per-item endings with who/where/evidence links — written elsewhere, displayed here. It answers “how did this end?”, not “end this”.
  12. Every row names its writer — release event, sweep, the person (and approver) on a task close, legal on a denial. Decided-by stays first-class at the moment of ending, where accountability matters most.
  13. Only Withdrawn and Previously-furnished are performed here — the two endings with no task to live in. Same popup pattern, same gates (withdrawal communication on file; the TX §552.232 certification). Previously-furnished appears only where its state provides it (rule-b posture).
  14. The parent's ending is derived, never chosen. All children terminal → Complete; mixed endings stay per-child; on an MRR the last child reaching ready already triggered Draft 7's settlement, and the last closure ends the MRR Management task.
  15. Access: from the request header, read-only for anyone with the request; no dedicated task type (nothing queues here). Who may perform the two manual endings is drafted RM / ORO Associate+ — open question below.

Columbus, OH in one line: no Previously-furnished path (TX-specific), the vagueness ending arrives via OH's denial ground instead of a clarification timeout where the city so chooses, no statutory deadline chip — every gate and the whole pipeline identical.
