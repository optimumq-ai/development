## 1. Taxonomy structure `[BUILT]`
Two levels: **categories** (15) → **record_types** (77 active; 84 incl. drafts). Rich per-type metadata (31 columns): synonyms, keywords, disambiguators, intent, expected_content, typical_request_reason, identifying_facets, formats, is_structured_data, public_availability, auto_release_eligible, redaction_profile_id, fee range, fulfillment_method, medium, auto_publish, mappable, status, source, confidence. Links: `record_type_departments` (roles **owner** and **fulfiller**, many-to-many) and `record_type_repositories` (types ↔ sources). Full CRUD + link management via taxonomy routes; managed on TaxonomyPage. Design Choice C (types and repositories as separate linked entities) — per TAXONOMY_DESIGN.md.
**Role gate `[BUILT 2026-08-18; verify_request_gates]`:** every taxonomy WRITE — categories CRUD, record types CRUD, department/routing/source/repository links, applying a variant proposal, AI `discover` and `discover-scan` (both insert drafts) — takes `middleware/auth.requireTaxonomyEdit` = `SYSTEM_ADMIN`/`DIRECTOR`: the "Workflow & Taxonomy" permission group of DESIGN_user_type_role_model §4–5 (Sys Admin + Director; team managers/supervisors hold no global config), and the same bar as redactionConfig / repository EDIT. Reads and the compute-only variant scan (`discover-variants` proposes, inserts nothing) stay `requireAuth`. Previously all `requireAuth` only. The Taxonomy tab and "Find Same-Format Records" remain VISIBLE to supervisors/team managers (nav is `isElev`); their write attempts get the server refusal in the editor's error line — hiding the write controls per role is a UI follow-on, not done here.
**Variants `[DECIDED + slice 1 BUILT 2026-08-13 — Kevin approved the model from mockups (`exchange/variant_mockups.png`); verify_taxonomy_variants 14/14]`.** A variant IS a record type that names its parent (`record_types.parent_record_type_id`) — no second catalog. **One level only** (enforced: no grandchildren, no self-reference, a bucket with variants cannot itself become a variant, deleting a bucket with variants is refused). A variant always sits in its **parent's category** (server-aligned, never trusted from the client). **Behavioral attachments inherit parent-ward** when the variant hasn't set its own: estimate profile (read-time fallback in `estimateProfile.getRow`), time budgets (variant → parent → generic in `taskBudget.lookup`), the legal-redaction gate (parent ON **binds** variants — a legal gate never loosens at a more specific level), owner/fulfiller routing (COALESCE walk-up in `classifier.catalogRows`), and `redaction_profile_id` when it gains a behavioral consumer. **Descriptive fields are always the variant's own** — they are what defines it. The classifier catalog shows variants as "Bucket — Variant" and is instructed to pick the variant only when the request clearly indicates it, else the bucket. UI: variants nest under their bucket on TaxonomyPage; the record-type editor gains a Parent field (category locked to the parent's). **Slice 2 `[BUILT 2026-08-13 — verify_variant_discovery 12/12; AI path probed live]`: auto-discovery groupings.** "Find variants" on any bucket row (TaxonomyPage) → `POST /taxonomy/record-types/:id/discover-variants` scans the bucket's linked sources (connector `scan()` samples + new `countAll()` for the REAL holding size where the connector can count — filestore can), and the AI groups the samples into proposed variants with `sample_share`, layout consistency, and a mass-redaction flag (uniform/few-layouts groupings only). **The scan inserts nothing** — proposals render in the mockup-3 modal with honest counts (`share × real total` when known, else "% of the scanned sample"), and each approval calls `POST /taxonomy/record-types/:id/variants` → `applyGroupingProposal` inserts ONE **draft** variant (parent + category aligned, `source='discovered'`, provenance sentence written into the description). Drafts don't classify — activation stays the human act. Existing variants are excluded from re-proposal; ungrouped share is reported and stays on the bucket.
**Fingerprint discovery — the deterministic census `[BUILT 2026-08-14 — Kevin's design; verify_fingerprint_discovery 18/18; AI naming path probed live]`.** The variant scan's middle is REPLACED for sources whose connector exposes real files (filestore's new `listFiles`): instead of an alphabetical first-50 sample squeezed through a 14k-char AI digest, **code reads EVERY document once** and stores a ~10-feature layout fingerprint (`services/docFingerprint`, persistent `document_fingerprints` table keyed by content hash — extract once, ever). Features are position-and-content based (page count, normalized first/last/mid-zone text with digits collapsed to `#`, first/last line positions with drift tolerance, line/word counts, and the page-1 **field-label set** — the text a template owns while values vary); two documents match at **8-of-10 agreement**, so a feature zone containing variable data can never break a match alone. The scan then runs **recognition before discovery**: fingerprints matching an already-approved variant's stored **consensus signature** (`discovery_meta.signature`, written at approval) are counted under the KNOWN variant — never re-proposed under a near-duplicate AI name — which is what makes the cross-location case work (same template stored in drive A until a date, drive B after: link the new drive, scan, recognized, template ready). Only the unrecognized remainder is clustered (union-find over pairwise 8/10 matches, min cluster 3); layout uniformity is MEASURED from within-cluster agreement, not guessed. **The AI's only remaining job is naming**: one small call with two excerpts + the label set per cluster; counts are exact cluster sizes (`counted: true` — the modal says "documents (counted)", and "Read and fingerprinted every document"), and image-only/unreadable files are excluded honestly (`unreadable` count shown). Approval stamps the cluster's fingerprints (`matched_record_type_id`) and stores the signature. Sources without file access keep the legacy sample-digest flow (`discoverViaSampleDigest`, unchanged). The old alphabetical-skew finding (2026-08-14 (i)) is thereby FIXED, not tuned. **Parked/future** (recorded 2026-08-14, Kevin's build-vs-document decision): OCR/vision fingerprinting for scanned archives (OpenCV registration territory) — image-only files are currently reported, not fingerprinted.

**Mass-redaction hand-off `[BUILT 2026-08-13 — Kevin approved from mockup (`exchange/mass_handoff_mock.png`); verify_mass_handoff 14/14]`.** An approved proposal flagged consistent-layout lands **machine-readable**, not just as description prose: `applyGroupingProposal` sets `record_types.mass_redaction_candidate = 1` and writes `discovery_meta` (JSON: `estimated_count` OR `sample_share` — never a fabricated count — plus `layout`, `example_files`, source `repos`, `found_at`; the approve call passes the scan's repo names along). The Mass Redaction page (`GET /redaction-templates/opportunities`) lists every flagged variant with **no un-deleted template naming it** as a **"Waiting for a template"** card — honest count sentence, example files, parent bucket. **Query-driven, no state to go stale:** "Start a template" runs the existing sample-upload flow carrying `?for_type=<variant>` so both save-as-template paths (pages + fields) link the new `layout_profiles` row to the variant, which clears the card; deleting that template brings the card honestly back; "Not needed" (`POST /redaction-templates/opportunities/:id/dismiss`, elevated-only) clears the flag by hand and leaves the variant untouched. Suggestions are cards on the page where the work happens — never tasks (the R10 notification/opportunity rule).

## 2. AI classifier & routing `[BUILT]`
One AI call does two independent steps: (1) match against the **active taxonomy** (compact catalog with synonyms/keywords injected) returning record_type + 0-100 confidence; (2) a **general-knowledge department guess**, with explicit instruction to return null rather than guess when off-topic/vague. Routing basis:
- **taxonomy** — confident type match → owner department; fulfiller team override honored (`record_type_departments.role='fulfiller'`).
- **general** — no type match but department guess → that department's processing team.
- **unassigned** — classifier abstains → request left team-less for the **triage queue** (never auto-stamped to a real team).
Confidence ≥ 70 also pins `record_type_id` onto the request (feeds estimate-profile lookup + task screens). Classification result + reasoning persisted to `workflow_decisions` for audit.

## 3. Embeddings & semantic layer `[BUILT]`

## 4. Schema discovery `[BUILT — propose/approve]`
`POST /taxonomy/discover` → connector `scan()` pulls sample documents from a repository → AI identifies distinct record types across samples → for each: either **matches an existing type** (linked to the repo) or **proposes a new one**, inserted as `status='draft'`, `source='discovered'` with confidence + example files. **Humans approve** by activating drafts on TaxonomyPage — drafts don't participate in classification (classifier uses active only). SchemaDiscoveryPage fronts this. Matches the AI-proposes/human-approves principle.
