## 1. Authentication & authorization `[BUILT / HARDENING items open]`
JWT access tokens (8h) carrying id/email/name/department + **function roles and permission roles**; `requireAuth` / `requireRole` middleware gates routes. **Shared write gates `[BUILT 2026-08-14 → 2026-08-18]`** live in `middleware/auth.js` so a bar cannot drift between route files: `requireRedactionWork` (processing surface — SPEC_redaction §6), `requireRequestWork` (a request's files — SPEC_record_search_task_screen §4a), `requireTaxonomyEdit` (SYSTEM_ADMIN/DIRECTOR — SPEC_taxonomy_classification §1), and the per-request ACT gate `middleware/requestAct.requireRequestAct` → `services/requestAccess` (acting role OR act permission OR the work is yours — SPEC_request_lifecycle_workflow §5a); config surfaces (redactionConfig, repositories) use `requireRole('SYSTEM_ADMIN','DIRECTOR')` inline. `SYSTEM_ADMIN` passes every gate; reads stay `requireAuth`. The same act gate covers `clocks.js` and `dispositions.js` since 2026-08-19 (SPEC_request_lifecycle_workflow §5a); onboarding's setup writes take `SYSTEM_ADMIN`/`DIRECTOR` with a designated-reviewer carve-out (SPEC_jurisdiction_configuration §5). **Inventory of what is STILL `requireAuth`-only at the middleware layer (2026-08-19, from `grep -n "router\.\(post\|patch\|put\|delete\)('.*requireAuth, async" src/routes/*.js` — 82 hits):** (a) carries its OWN in-handler authority — requests.js reopen/route/fee-waiver/legal-escalate/commercial, dispositions.js knobs + manual endings, onboarding.js approve, mrr.js (Request-Manager / assignee checks on the activity, estimate-data and generate-estimate acts), tasks.js (assignee-or-mayRoute on intake-routing / work / finalize; claim/begin/resolve/close/close-approval/release-review carry pool-eligibility and role checks in-handler), legalEstimate.js complete (assignee), redactionTemplates.js create/edit/delete/dismiss/apply-batch (isElevated), objections.js approve (`requireRoleOrPerm`); (b) compute-only or own-record — classify, estimateProfiles assess, feeProfiles extract/preview, feeSandbox preview, structuredRedaction preview, template match/match-batch, files search, taxonomy discover-variants, semanticSearch, help/reports ask, notifications read/dismiss, auth password change, config dashboard-panes (the caller's own layout); (c) **NOT YET AUDITED — the next hardening pass:** `feeEstimates.js` (11 request-money acts: create estimate, send notice, de-minimis waive, accept/decline, deposit / final-payment / payment record, reconcile, adjustment + notice, reopen), `objections.js` create/assign/resolve, `settlement.js` charge, `departments.js` create/edit/fulfills (org config — SYSTEM_ADMIN/DIRECTOR by the design model), `feeProfiles.js` create/edit (Fee Configuration group), `agentRules.js` CRUD (portal-agent security — SYSTEM_ADMIN), `tickler.js` clear/:requestId, `legalEstimate.js` ask, `mrr.js` priority / designate-denial / withdraw / mark-defect / hold / lift / release (verify each carries an RM check). Per-request money acts belong to the act gate (`requireRequestAct`, FINANCE / FEE_MANAGER perms); config surfaces belong to `requireRole('SYSTEM_ADMIN','DIRECTOR')`. Password hashing: **SHA-256 with a static salt** (the bcrypt-deadlock workaround) — `[HARDENING: upgrade to a proper KDF (bcrypt/argon2) + per-user salts pre-production]`. No MFA `[HARDENING — PRE_RELEASE_HARDENING Category 2]`.

## 2. Secrets `[BUILT / HARDENING]`
On-prem key handling: customer-provided keys stored in `system_config`, loaded into `process.env` at boot so all call sites work unchanged; saved keys override the `.env` baseline. **Stored plaintext** — `[HARDENING: encrypt-at-rest pre-production]`. Never echoed/SELECTed in ops (standing rule).

## 3. Departments & teams `[BUILT]`
`departments` with `kind` (department vs team), `is_open_records`, `is_catch_all`, `processed_by` (department → its processing team), **`auto_load_balancing`** (per-team toggle — the Tasks-spec §3 toggle EXISTS), `routing_specialization`, active/sort. DepartmentsPage + StaffManagementPage front org + user/role assignment.

## 4. Email `[BUILT]`
Resend integration, **live** — key + `resend_from` from system_config (optimumq.ai domain verified); `onboarding@resend.dev` is an unused fallback only. Branded templates (emailTemplate). Used by: verification, onboarding review requests, estimate/adjustment notices, dunning.

## 5. Platform `[BUILT]`
Ubuntu droplet; **PM2** (optimumq-api :3001 + three demo-connector stubs) running as dedicated **`optimumq` service user** (de-rooted 2026-07); nginx serves the built frontend; **PostgreSQL + pgvector in Docker**; geocode service for the map. Background workers on boot: massJobs, nena911 scheduler, importIngest scheduler, tickler, configFreshness, task reconciler.
