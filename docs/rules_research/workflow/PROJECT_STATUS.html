OptimumQ — Public-Records Rules & Workflow

Project status & orientation · prepared 2026-07-24 · read this first
What this project is, in one paragraph. We are building a system that can process public-records requests correctly in any U.S. city. Different states have very different rules, so the plan is: (1) gather each state's actual rules, (2) strip out everything the system doesn't act on, (3) collapse the thousands of individual rules into a small set of shared "concepts," and (4) design one master workflow where the shared logic is written once and each state's differences are handled as either a configurable value (e.g. a due-date number) or an on/off branch that activates only for that state. We are currently between step 3 (done) and step 4 (in progress).

Things decided along the way (so you don't have to re-derive them)

  • Parent vs child. A request (parent) holds up to 10 items (children). Work-status lives on each child; money/accounting lives on the parent. The only override: the parent can put a child on Hold–Awaiting Payment or Closed–Nonpayment.
  • Compliant automation only. Where a state's step can't be cleanly automated, the system does the compliant subset and leaves that step manual — it never ships something automated-but-non-compliant.
  • "Config, not law" edges. Several sequencing steps (how long a requester has to respond to a clarification or an estimate, when to close for non-payment) are not written into most states' laws — so they become configurable city policies with sensible defaults. The diagrams flag these with a ⚠.
  • Requester-class states. Alabama, Idaho, Virginia, Tennessee, Pennsylvania restrict who may request (residency/citizenship). That's a config dimension, not a reason to exclude those states.
