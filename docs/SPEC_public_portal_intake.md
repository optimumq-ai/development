## 0. Architectural invariant — the request is born only at Submit `[INVARIANT — LOCKED 2026-07-18]`
**The entire intake flow is client-side state until the citizen presses Submit. The request row (parent + children), the statutory clock, and every downstream side-effect come into existence in ONE transaction at `POST /public/submit` (`requestCreate.createRequest`) — never before.**

Grounded in code (verified 2026-07-18):
- A citizen request has exactly ONE birth site — `createRequest`, called only from the submit route (`publicChat.js:374`). Nothing in the pre-submit flow writes a `requests` row.
- The AI chat (`/public/chat`) persists nothing; the per-item searches (`/native-search`, `/refine-search`, `[[SEARCH_QUERY]]`, `[[EMAIL_SEARCH]]`) are read-only. The only pre-submit write is a self-expiring `email_verifications` token (carries `expires_at`, no clock, no worklist, no obligation).
- The statutory clock starts at creation (`tolling.startClocks`), i.e. at Submit. Before Submit there is no clock to breach and no row to reap.

Consequences (all three are the reason the invariant is stated, not left implicit):
1. **Abandonment is a non-event.** A started-but-abandoned session never becomes a row, so nothing has to be *identified* as abandoned or *forgotten*. No `draft` status, no reaper/cron, no orphan cleanup — that machinery does not exist and is not needed.
2. **No mid-loop persistence — the trap this invariant guards.** The per-record loop's mid-flow actions — "Submit for Open Records team search", record selection, marking an item complete — MUST be buffered in browser state and flushed in the single submit payload (`searchIntents[]` / `selectedRecords[]` / `children[]`). A mid-loop write that routed a child into a worklist before Submit would strand an orphan child under no parent the instant the citizen closes the tab — the silent-orphan failure this project is scarred by. On the results screens, **"Submit" means _tag this item's disposition_, not _persist and route now_.**
3. **No citizen-driven abandonment after Submit either.** Once submitted, a request is a live statutory obligation the city must fulfill on the clock; only the city closes it, per statute. "Abandoned" applies to nothing in the persisted model.

Accepted tradeoff (v1): zero pre-submit persistence means a citizen who loses their browser mid-session loses the in-progress entry — there is no save-and-resume. This is deliberate for v1 (simpler; no half-built PII at rest; no reaper). **If save-and-resume is ever adopted it is a deliberate future decision that ADDS** a `draft` request status that does NOT start the statutory clock **and** a scheduled reaper that deletes stale drafts — neither may be introduced implicitly. `[FUTURE — DEFERRED]`

Applies to BOTH the current split-canvas intake (§2b) and the wizard / one-item-loop redesign under discussion (`uploads/portal flow and screenshots.doc`; mockups `uploads/screen*.xls`). See `SPEC_parent_child_lifecycle.md` for the parent/child model this protects.

## 2. Intake chat agent (AI, Anthropic API) `[BACKEND BUILT — chat-first frontend flow RETIRED 2026-07-10, superseded by §2b]`
The chat-first request UI (contact form → verify → describe → search → fee → submit, all in one conversation) is **retired and removed**: `/portal`'s Create button opens the split-canvas flow (§2b), and `PublicPortalPage` is now just the landing chooser (the chat/form/native-search render was deleted 2026-07-10). The `/public/chat` endpoint + default (non-split-canvas) system prompt are **retained on the backend**; the split-canvas flow reuses the same endpoint with `mode:"split_canvas"`. The phase/marker reference below documents that shared backend.
Phased conversation; agent emits bracketed markers the system acts on.
- **Phase 1 — Contact:** greet, emit `[[CONTACT_FORM]]` → one form (name, email, phone-optional). Optional email verification: `[[VERIFY_EMAIL:addr]]` sends a real verification email (Resend, live) and waits; `[[VERIFY_SKIPPED:addr]]` proceeds. Then delivery preference (email | postal).
- **Phase 2 — Description:** elicit records sought; clarify one question at a time (dates, departments, people/events, format); confirm scope in plain language.
- **Phase 2.4 — Format fork:**
  - **PATH (a) documents/forms/police video** → searchable; go to 2.5.
  - **PATH (b) email/text, audio, photos, database exports, paper** → no library search; explain once, warmly; gather targeted details (senders/recipients + date range for email; date/location/incident for AV; event/date/location for photos); skip search.
  - **Email/text special case:** `[[EMAIL_SEARCH:terms]]` runs a **count-only** search (no content exposed); agent relays only the count and helps narrow if large (count-then-narrow).
- **Phase 2.5 — Library search (PATH a):** `[[SEARCH_QUERY:...]]` → system searches; results injected as UNTRUSTED DATA; result-aware reply asks "any match?" (quick replies). Citizen selections are injected into agent context and **persisted on the request at submit**; agent will not re-search after selection and moves to finalize.
- **Phase 3 — Multi-record handling:** the per-record intake loop produces **one item per described record** under **one request** (one number, one parent-level fee). **No "combined vs separate" question** — combining is the default and the only path (MRR model, `SPEC_tasks_roles_mrr_fees.md` §12). The only ≥2-item choice is **delivery timing** (each-as-ready vs hold-all). `[SUPERSEDES the old "ask combined vs separate / mrrChoice" design — that question is retired]`
- **Phase 4 — Fee waiver:** yes/no public-interest question → `[[FEE_WAIVER_INFO:yes|reason]]`. `[BUILT — superseded by §5 design]`
- **Phase 5 — Confirm & submit:** summary → explicit confirmation → `[[SUBMIT_READY]]{json}[[END_SUBMIT]]` with contact, delivery, description, feeWaiver, isMrr. `[mrrChoice retired — combining is the default; delivery-timing (each-as-ready vs hold-all) replaces it, §12]`
- **Quick replies:** `[[QUICK_REPLIES: A | B]]` tappable buttons; max one per message; only for closed questions; typing always works.

## 2b. Split-canvas intake (`/portal/split-canvas`) `[RETIRED as the request flow 2026-07-18 — kept for rollback]`

The split-canvas portal (design: `DESIGN_split_canvas_intake.md`) inverts the intake model: a **Phase-0 structured form** (left canvas) owns identity, email-accuracy gate, delivery, mailing address, fee-choice, and certification; the **chat agent** (right panel) does ONLY record **descriptions + search + the one-record-at-a-time (MRR) loop**. Reached from the `/portal` landing's "Create an Open Records Request" (canonical URL `/portal/request`; `/portal/v2` redirects there).
- **Backend agent flow** `[BUILT — slice 3]`: `POST /public/chat` with `mode:"split_canvas"` selects `SYSTEM_PROMPT_SPLIT_CANVAS` (`publicChat.js`). It reuses the full search stack (`[[SEARCH_QUERY]]` → library search + AI relevance judge; `[[EMAIL_SEARCH]]` count-only for email/text; PATH (a)/(b) format fork; result-aware second-pass reply; `[[QUICK_REPLIES]]`) but **never** collects contact info, verifies email, asks delivery/fees, or emits `[[SUBMIT_READY]]`/`[[CONTACT_FORM]]`/`[[VERIFY_EMAIL]]`/`[[FEE_WAIVER_INFO]]` — those markers are barred; the form owns them. Result-aware and no-result reply text is mode-aware (points at "the results view", not chat cards; never re-asks for delivery). Default (chat-first) `/portal` flow unchanged.
- **Opening script** is the verbatim design greeting, seeded **client-side** (display-only), so it is never sent to the API (Messages API needs a user-first turn); the first API call is the citizen's first description.
- **Frontend chat engine** `[BUILT — slice 3]` (`PublicPortalV2Page.js`): PROCEED activates the panel, real user/assistant turns, typing indicator, tappable quick replies. A search response's records flow to the results canvas (not chat); that turn's "any match?" quick replies are suppressed in chat since selection is canvas-driven.
- **Results canvas (Phase 2)** `[BUILT — slice 4]`: on PROCEED the left panel **morphs** from the form to the results box (full-width instruction banner + results grid + ~27% Selected-Records column). Ticking a record moves it to the Selected column (removable). **Canvas Proceed** performs **per-child attach-and-clear**: the current record's selection attaches to a child (`children[]`), both panels clear, and a "selected N records" turn is sent to the agent (with the cumulative `selectedRecords`), which then asks **"describe another record?"** — Yes reopens a fresh canvas for the next description; No hands to submit. Zero-result / PATH-(b) searches show no grid and stay chat-driven. The superseded "download-now vs submit-all" fork is **not** built (locked decision: immediate records fulfill via the library path at submit, no in-panel download).
- **Submit** `[BUILT — slice 5]`: a **"Review & submit request"** button appears in the results side-panel once ≥1 record is added; it opens a review scrim (contact · delivery/address · certified · fees · per-record list with selection counts) → **Submit** POSTs `/public/submit` and shows the request number. The request's `description` is the described records joined (`Record N: …` when >1), `selectedRecords` = every attached child's picks, `is_mrr` when >1. Records the citizen could not pick from results (zero-match or PATH-(b)) are captured via a new agent marker `[[RECORD_ADDED:desc]]` (returned as `recordAdded`, stripped from view). **Certification** (`certification_requested`) and the **email-accuracy method** (`email_verification_method ∈ {attested,visual}`) are now persisted (new columns) alongside the slice-1 fields.
- **Mobile step-through** `[BUILT — slice 6]`: ≤860px shows ONE surface at a time with a sticky **Form/Results ↔ Assistant** toggle (Assistant disabled until PROCEED; unread dot when an agent message arrives while off-chat). Driven by the same phase transitions as desktop — PROCEED → chat; search results → canvas (+ unread); canvas Proceed → chat ("another record?"); Review → canvas. The Selected-Records column stacks below the results list. All behind `@media (max-width:860px)`; desktop side-by-side is untouched.

Persists to a new **`request_search_intents`** table (per-description row: description, intent, queries tried) + `request_selected_records.intent_id` — the per-child row the flattened submit never had. ## 2c. Wizard redesign `[BUILT + LIVE 2026-07-18 — serves /portal/request]`
Kevin's wizard / one-item-at-a-time portal redesign (mockups `uploads/screen*.xls`; flow narrative `uploads/portal flow and screenshots.doc`), walked and agreed 2026-07-18, then BUILT in 5 React slices (`frontend/src/pages/PublicPortalWizardPage.js`, scoped `.pwz`, both themes) and **cut over to `/portal/request` 2026-07-18** (split-canvas → `/portal/split-canvas` for rollback). Prototype: `frontend/public/prototypes/portal-wizard.html` (served `/prototypes/portal-wizard.html`). **⚠️ Live chat unverified against the real agent — Anthropic credits were exhausted at cutover, so `/public/chat` (both flows) and intake classification are down; slices 3–4 were verified by mocking. Restore credits + smoke-test the real describe→search round-trip before treating the portal as production-ready; also confirm the Case-B backend signal (`searchResults:[] + searchQuery`).** *Rationale Kevin confirmed in review: the structured form is easier for a human to complete AND narrows the agent's job to record descriptions only — fewer turns, no free-text parsing of identity/contact facts, a smaller agent-error surface (the §2b "chat is a clumsy way to collect structured facts" bet, now validated in use).* It **reuses** the existing intent model — the §2.4 format fork (PATH a searchable / PATH b not-searchable) and the §2b R9 dispositions (`complete` / `search_more` / `no_match_search` / `not_searchable`); it does not invent a parallel one. Governed by §0 (client-side until Submit). **RECONCILED 2026-07-18 — the wizard is the RATIFIED target shell** (Kevin's call, usability-driven). The §2b split-canvas **SHELL is superseded**; its backend, the submit-payload assembly, search/selection/refine logic, verification data-plumbing, and the 3-layer design palette are the **REUSE SUBSTRATE** (reusability audit of `PublicPortalV2Page.js`: ~⅓ carries as-is, ~¼ reworks into steps, ~40–45% is presentation rebuilt for the wizard). Split-canvas stays LIVE at `/portal/request` until the wizard replaces it. This section is now the target contract, not just a candidate.

**Agent is description-only.** The chat agent gathers + refines one record description; on "submit for search" it **hides**. Everything after a search is **click-driven in the results window** — match AND no-match alike. The agent is never re-summoned mid-results (keeps agent tasks narrow).

- **G1 — two honest "no records to select" screens, auto-selected.** The old single "NO MATCHING RECORDS LOCATED" conflated two states and misled requestors about team-searched types (records may well exist). Split, chosen from state the system already holds (no new AI judgment):
  - **Case A — not-searchable (PATH b):** no search ran. Header *"This type of record is searched by our staff"*; body: paper/email/audio/photos aren't in the instant catalog, **this doesn't mean they don't exist**, staff search by hand.
  - **Case B — searchable, 0 results (PATH a):** a search ran, nothing came back. Header *"No instant matches found"*; body: the catalog isn't everything, staff may still locate records.
  - Both lead with the **primary blue** CTA *"Submit for Open Records team search"* (`no_match_search`); *"Remove item"* is the quiet secondary.
- **G2 — one shared phrase, two intents, for team-search escalation.**
  - Not-searchable / no-match → **"Submit for Open Records team search"** → `no_match_search` (team is the sole fulfiller).
  - Match, records already selected → **"Also search with the Open Records team"** → `search_more` (keep selected records AND escalate for more). The **"Also"** is deliberate — additive, not instead-of.
  - Item badge (short, both cases): **"Team search"**. Drops the ambiguous "Internal Search" wording.
- **G3 — per-record selection; completion button reworded.** Selection is per-record (checkboxes → Selected column, as built §2b), never all-or-nothing.
  - Completion button reworded from "All records for this search item are located and selected" (a claim about the city's holdings the requestor can't make) → **"Use selected records — item complete"** → `complete`. Enabled only when ≥1 record checked.
  - Optional **"Select all"** convenience link, separate from the completion button.
  - **Transparency line** on the match screen: results may be partial (older/paper records won't appear); if the requestor believes more exist, they use "Also search with the Open Records team." (Driven by the digitized-vs-paper scenario — a requestor selects digitized permits but suspects paper ones exist; `search_more` lets them say "take these AND find the rest" without knowing what's digitized.)
- **G4 — "Remove item" + empty-request guard.** Term is **"Remove item"** (not "Discard" — avoids reading as *discard the whole request*). Free under §0 — drops client-side state only; no DB row, no orphan.
  - Available on **every** results screen (match, no-match, not-searchable), resolving the asymmetry. It is the **substitute for "revise"** (remove + add fresh; no revise button — 2026-07-17 decision).
  - **Confirm before remove** (*"Remove this item? This can't be undone."*) — no draft/undo (§0).
  - Removed items **free their slot** toward the 10-item cap.
  - **Guard:** "Submit Request" is enabled only when ≥1 item is in a kept disposition (`complete`/`search_more`/`no_match_search`/`not_searchable`). Removing the only item → land on Submit-or-Continue with Submit disabled, "Continue with next item" the only path. **A request can never submit zero records.**
- **G5 + comms policy — email-only communication, on-screen number authoritative.**
  - **Email is the SOLE communication channel; postal is records-DELIVERY only** (`delivery_method = postal` → mailing address for shipping, decoupled from comms). Rationale: portal use self-selects for email; the certified-mail / legal-formality path lives OUTSIDE the portal (staff intake); the non-digital cohort is served elsewhere. **Assumption to keep conscious:** the city MUST maintain a real, advertised non-portal intake channel (in-person / mail / phone) for no-email / no-internet citizens (equal access). The email-only portal is defensible *because* that parallel lane exists.
  - **Screen 1's "I don't have access to email / visually verified" fallback is DROPPED** (self-contradictory: email required, but unreachable).
  - **Confirmation:** the on-screen **request number is authoritative**, shown at the Complete step for everyone; a confirmation email is a **copy** (always possible since email is required), never the sole path. Copy leads with "save this number." The number doubles as the **status-check fallback** if email delivery fails.
  - **Print / Save-PDF confirmation → v1.1 deferred** (on-screen + save-the-number suffices for launch).
  - **Mandatory email verification — real link-click, STRICT gate (option A), no skip.** Enter email → send link → requestor clicks link → **THEN** the rest of Screen 1 unlocks. No "proceed unverified" path (also barred by §0 — no number before Submit). Communicated **very early** ("to create a request you must provide an email and click the verification link"). The link round-trip is **already built** (`POST /request-verification` → `GET /verify/:token` → `GET /verify-status` poll, `publicChat.js:497–554`); remaining work is: remove the skip/attest paths, wire the verified-state gate, add a **"Resend link"** affordance (30-min token expiry), and a minor template fix (verify page says "return to the chat" — it's the form now). Cross-device works (click on phone → desktop poll detects).
- **Progress bar** (author-flagged): delete "Complete"; rename "Review and Submit" → "Submitted." No separate review-document screen for v1 (deferred; if adopted later, "Submit Request" becomes "Submit for Review"). Effective nodes: Begin · Your Information · Item Search · Submitted.
